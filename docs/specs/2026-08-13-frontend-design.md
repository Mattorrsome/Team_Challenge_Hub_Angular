# Team Challenge Hub — Angular Frontend Design

**Date:** 2026-08-13 (consolidated)
**Status:** Approved — implemented
**Companion spec:** `../../../Team_Challenge_Hub_API/docs/specs/backend-design.md`
(API-side, source of truth for auth mechanics, the ownership rule, DTO shapes,
and the AI-draft failure contract)
**Decision log:** `../superpowers/plans/decisions.md`

This is the single current-state spec for the frontend. It replaces the eleven
per-feature specs written between 2026-07-27 and 2026-08-11; where those
contradicted each other, the later decision won. Rejected and superseded
approaches live in the decision log, not here.

## Problem Statement

Team members need to submit delivery challenges, refine them into clear problem
statements with AI assistance, review AI-generated solution option drafts,
edit/accept them, and track a selected option through a review workflow — behind
real sign-in, on a responsive UI that works in light and dark themes.

## Scope

In scope:

- Credential sign-up / sign-in against the API's cookie session, with route guards
- Challenge list: scoped to the signed-in user (unscoped for admins), status filter
- Create / edit challenge form
- Challenge detail: one step's panel at a time, AI-draft-assisted problem statement
  and solution options behind a human accept gate, status stepper, delete, author byline
- Admin-only user management (list, change role, delete)
- Light/dark theming on the brand palette, mobile-friendly layout throughout

Out of scope (do not build toward these):

- Password reset, email verification, MFA, sign-in rate limiting, multi-session management
- Real-time multi-user collaboration, notifications/email
- Pagination — small demo dataset, the list loads everything at once
- Deleting solution options (`DELETE /api/challenges/{id}/options/{optionId}` has no UI)
- Delete from list cards; "yours" badge, owner column, author filter or sort
- Undo, soft delete, or a trash view — the API deletes immediately and cascades options
- Ownership transfer, co-owners, per-challenge permission grants
- Visual-regression testing; any client-side authorization logic beyond the
  `canEdit` affordance
- Per-user hashed username colors

## Tech Stack

- **Angular 22** (22.0.8) — requires Node.js `^22.22.3 || ^24.15.0 || >=26.0.0`
- Standalone components, no NgModules
- Angular Material 22.0.8 (M3 theming) for UI primitives
- Angular Router; `HttpClient` with functional interceptors; `httpResource()` for
  the reactive challenge list; Reactive Forms for input; signals for component state
- SCSS
- **Vitest** (`@angular/build:unit-test`) for unit tests — not Jasmine/Karma
- Playwright for end-to-end tests

## Coding Conventions

- Component class files use the legacy `.component` suffix
  (`challenge-list.component.ts`), generated via
  `ng generate component <path> --style=scss`.
- Every component has separate `.component.ts` / `.component.html` /
  `.component.scss` files — no inline `template`/`styles`.
- One component per file/folder; folder name matches the component selector base.
- Services use `.service.ts`; models use `.model.ts` (or plain `.ts` under
  `models/`); route config uses `.routes.ts`.
- Standalone components declare explicit `selector`, `standalone: true`, typed
  `@Input`/`@Output` — no implicit `any`.
- `inject()` for DI, `ChangeDetectionStrategy.OnPush` on every component, strict
  TypeScript mode.
- Vitest matchers only (`.toBe(true)`, never Jasmine's `toBeTrue()`).

## Architecture

```
src/app/
  core/
    models/                # Challenge (+ ChallengeStatus, STATUS_LABELS), SolutionOption, User
    services/              # challenge-api.service.ts, user-api.service.ts
    auth/                  # auth.service.ts, auth.guard.ts, admin.guard.ts, models/auth-user.model.ts
    theme/                 # theme.service.ts
    interceptors/          # credentials.interceptor.ts, error-handling.interceptor.ts
  features/
    challenge-list/
    challenge-form/        # shared create/edit form
    challenge-detail/
      problem-statement-panel/
      solution-options-panel/
      status-stepper/
    auth/
      sign-in/
      sign-up/
    admin/
      user-management/     # admin-only: list users, change role, delete
  shared/
    status-badge/
  styles/
    _theme-colors.scss     # generated by the Material schematic — never hand-edited
```

No shared library between this frontend and the backend — the DTO contract is
documented in both specs and kept in step by hand. Scale doesn't justify a
shared package.

`proxy.conf.json` targets the sibling API's Kestrel dev port
`https://localhost:7261`, with `http://localhost:5179` as the documented
fallback. Playwright must run against the API's **`http`** launch profile: the
`https` profile binds both ports, so `UseHttpsRedirection()` 307s a proxied
request on 5179 to the HTTPS origin, which the browser treats as cross-origin
and drops the `SameSite=Lax` session cookie.

## Auth & Roles

`core/auth/` holds:

- `AuthService` — `currentUser: Signal<AuthUser | null>`, `isAdmin: Signal<boolean>`,
  `loadCurrentUser()` (401 maps to `null` and never throws), `signIn`, `signUp`
  (the API auto-signs-in the new account), `signOut`, and `clearCurrentUser()`
  for dropping a session the server has already invalidated.
- `authGuard` — allows a signed-in user through, otherwise a `UrlTree` for `/sign-in`.
- `adminGuard` — allows `role === 'Admin'`, otherwise a `UrlTree` for `/challenges`.
- `AuthUser { id, username, role }` with `UserRole = 'Collaborator' | 'Admin'`.

`provideAppInitializer` awaits `loadCurrentUser()` before the first navigation,
so `authGuard` reads a settled `currentUser` instead of racing `/auth/me`.

The session is an HttpOnly signed cookie: `credentialsInterceptor` sets
`withCredentials: true` on every request and **no token is ever handled in
application code**. `authGuard` protects every route except `/sign-in` and
`/sign-up`; `adminGuard` additionally protects `/admin/users`.

Sign-in/sign-up are Reactive Forms showing errors inline, never as snackbars:
bad credentials (401) → a generic "Invalid username or password." (the API
deliberately doesn't reveal whether the username exists); a taken username (400
`{errors: {Username: [...]}}`) → a `server` error on the username control, which
its own `mat-error` renders, so the generic error block must not repeat it.

A failed `signOut` leaves the user signed in and stays put — navigating to
`/sign-in` would claim a sign-out that didn't happen.

## Ownership

**A challenge's content is owned; its workflow is shared.**

```
canEdit = auth.isAdmin() || challenge.submittedByUserId === auth.currentUser()?.id
```

Computed once in `challenge-detail`. This mirrors the API's `DenyIfCannotEdit`
and is the only place the rule is written on this side — never add a second copy.

- **Owner-or-admin** (403 otherwise, server-side): `PUT /api/challenges/{id}`,
  `DELETE /api/challenges/{id}`, `POST /api/challenges/{id}/options`,
  `DELETE /api/challenges/{id}/options/{optionId}`,
  `PUT /api/challenges/{id}/options/{optionId}/select`.
- **Open to every signed-in user**: both `GET`s, both `draft-*` endpoints,
  `POST /api/challenges`, and — deliberately — `PUT /api/challenges/{id}/status`.
  Gating status would let an owner approve their own challenge, making review a
  formality.
- Existence is checked before ownership: a missing challenge is **404**, someone
  else's is **403**.

`canEdit` is a UX affordance, not a security boundary. The API is the enforcement
point; the UI only avoids offering actions that would 403. Never remove a
server-side check because the UI hides the control.

In `challenge-detail`, `canEdit` gates the Edit Title link, the Delete button,
and the whole `problem-statement-panel` (everything in it is an editing
affordance, and the accepted statement is already rendered read-only by the
parent). `solution-options-panel` takes a `canEdit` **plain `@Input`** (read as
`canEdit`, no parentheses — unlike the parent's computed signal) and, when
false, renders only its heading and the read-only accepted-options list.
`status-stepper` is never gated.

The challenge list sends `userId = currentUser.id` for a collaborator and omits
the param entirely for an admin — which is what makes the admin's edit override
reachable through the UI rather than dead flexibility.

## Data Flow

1. App init: `AuthService.loadCurrentUser()` resolves the cookie via
   `GET /api/auth/me`. Unauthenticated visitors are sent to `/sign-in` by `authGuard`.
2. Challenge list: `challengesResource(() => ({ status, userId }))` — an
   `httpResource` keyed on the status-filter and current-user signals, so it
   re-fetches on either change and supersedes any in-flight request. (An
   `effect()` cannot cancel, so two rapid changes could leave the wrong user's
   challenges on screen.) `null` params are omitted from the query string.
3. Create: `POST /api/challenges` (title, raw notes; the submitter comes from the
   session) → status `Submitted`.
4. Problem statement: `POST /api/challenges/{id}/draft-problem-statement` returns
   `{ problemStatement }`, shown in an **editable textarea**, not saved. The user
   edits, then "Accept & Save" → `PUT /api/challenges/{id}` persists it and
   advances the status.
5. Solution options: `POST /api/challenges/{id}/draft-solution-options` returns
   `{ options: string[] }`; each draft is editable and accepted individually via
   `POST /api/challenges/{id}/options`.
6. Selection: `PUT /api/challenges/{id}/options/{optionId}/select` → `OptionSelected`.
   The owner may switch the selection while the status is `OptionsDrafted` **or**
   `OptionSelected`; the API decides whether the change is legal and answers 409
   if not.
7. Status: `PUT /api/challenges/{id}/status` from the stepper.
8. Delete: `deleteChallenge(id)` from the detail page, behind a native `confirm()`,
   then navigate to `/challenges`. Routing there constructs a new
   `ChallengeListComponent`, whose resource is a field initializer, so the list
   re-fetches with no explicit invalidation.

### Status flow (shared contract with the backend)

```
Submitted → ProblemStatementDrafted → OptionsDrafted → OptionSelected → InReview → Approved
                                                                                 ↘ Rejected
```

The stepper **does not hardcode transition rules**. It renders all steps as a
progress trail, shows only the transition buttons the data flow defines as
stepper-driven (`InReview`, `Approved`, `Rejected`), and defers to the API, which
returns 409 on an invalid transition.

`STATUS_LABELS: Record<ChallengeStatus, string>` is exported from
`core/models/challenge.model.ts` and is the single source of display text,
consumed by both `status-badge` and the list filter, so a status cannot pick up
two spellings. The `Record` type keeps it exhaustive — adding a status without a
label is a compile error. The filter's `[value]` still binds the raw enum, so the
request payload is unchanged.

### Human review gate (AI content)

Every AI-draft endpoint is read-only on the server. The frontend always routes AI
output through an editable field and an explicit "Accept & Save" before any
persisting call. **There is no code path where AI-generated text reaches the
database without a human clicking accept**, and none may be added.

## Challenge Detail Layout

Template order: header row (`h2`, `app-status-badge`, and — when `canEdit` —
Edit Title + Delete) → author byline → `app-status-stepper` → raw notes →
read-only problem statement (when set) → selected option (only at `InReview`) →
the single status panel.

One panel at a time, via a `currentPanel` computed:

| Status | Panel |
|---|---|
| `Submitted` | `problem-statement` |
| `ProblemStatementDrafted`, `OptionsDrafted`, `OptionSelected` | `solution-options` |
| `InReview`, `Approved`, `Rejected` | none — the badge and the stepper's own buttons cover this stage |

**`ProblemStatementDrafted` maps to solution-options, not problem-statement.**
It is the state whose next action is adding an option: the API's `AddOptionAsync`
accepts only `ProblemStatementDrafted` or `OptionsDrafted` and auto-transitions
the former to the latter on the first option, and the app's only `addOption`
caller lives in `solution-options-panel`. Mapping it to the problem-statement
panel dead-ends the workflow permanently — the challenge can never reach
`OptionsDrafted`.

Because the accepted problem statement leaves the editable panel once the flow
moves on, `challenge-detail` renders it as read-only text — otherwise the user
would draft solutions to a problem they cannot read; the raw notes are not the
refined statement. Accepting the problem statement is therefore a one-way step.

A 404 on load sets `loadFailed` and shows "Challenge not found." with a link
back, rather than spinning forever.

### Author byline

One rule on both screens: **show the author when the challenge is not yours.**

- `challenge-detail`: `authorName` computed, rendered as `Submitted by {{ name }}`
  in a `.challenge-detail__author` paragraph below the header row (a bare name
  inside that flex row would read as another control).
- `challenge-list`: `myId` computed, compared per card in the template; the name
  renders in `mat-card-subtitle`, Material's own slot under the title, with no
  label needed.

There is deliberately **no admin gate** — it falls out of the ownership rule for
free. A collaborator's list is scoped to their own challenges, so no byline ever
renders there; an admin's unscoped list shows one on everyone else's cards and
none on their own; and a collaborator who opens a peer's challenge by URL (which
the shared status workflow permits) sees it too — the case an admin-gated rule
would have got wrong.

The name comes from `challenge.submittedByName`, supplied on every `ChallengeDto`.
No second request, no id→name map: `GET /api/users` is admin-only and cannot
serve a collaborator viewing a peer's challenge. It is a display name, never a
login handle — the API deliberately keeps `Username` off `ChallengeDto`.

### Solution options panel

Order: heading → accepted-options list → drafting block. The drafting block
(inline error, Draft button, draft editors) is hidden once the status reaches
`OptionSelected`; the accepted list is all that remains from that point.

The selected row carries `.solution-options-panel__selected-row` and is marked
with a filled `check_circle` `mat-icon` (`role="img"`, `aria-label="Selected
option"`, `aria-hidden="false"`, plus a tooltip); a selectable row gets an
outlined `radio_button_unchecked` icon button labelled `Select option: <text>`.
The two states differ by glyph shape, not merely by fill.

`aria-hidden="false"` is required, not boilerplate: `MatIcon`'s constructor
force-sets `aria-hidden="true"` whenever the template omits the attribute, and
only an explicit `"false"` survives that guard, keeping `role="img"` and
`aria-label` reachable by assistive tech.

## Theming

Brand palette:

| Role | Value | Usage |
|---|---|---|
| Dark surface | `#070c14` | Dark-theme background |
| Light surface / dark-theme text | `#ffffff` | Light-theme background; text on dark |
| Secondary / interactive | `#007FBA` | Buttons, active/selected states, focus rings |
| Sparse accent | `#FFC72C` | Links and small emphasis ONLY — never a background or large surface |

**Mechanism: Angular Material's `theme-type: color-scheme` plus CSS
`light-dark()`.** `mat.theme()` with `theme-type: color-scheme` emits every
`--mat-sys-*` color as a `light-dark(light, dark)` pair, so `ThemeService`
switching the `color-scheme` property on `<html>` flips the entire app —
including every Material component — with no per-component dark styling.

- Palettes are **generated from the brand seeds** by
  `ng generate @angular/material:theme-color` (`#007FBA` primary, `#FFC72C`
  tertiary, `#070c14` neutral) into `src/app/styles/_theme-colors.scss`, which is
  never hand-edited. `mat.theme()` requires M3 palette maps, not raw hex.
- `mat.theme-overrides` then pins `surface` and `on-surface` to the exact brand
  hex, so the background is exactly right while everything else keeps M3's
  derived contrast.
- `ThemeService` persists the choice in `localStorage` under `tch_theme`
  (`light`/`dark`); an inline script in `index.html` applies it before first paint
  to avoid a flash of the wrong theme. Both must agree on that key and those values.
- **Never emit `color-scheme: light dark`** — this app follows the user's explicit
  choice, not the OS setting.

Rules for new styling (also in the `team-challenge-colors` skill, which is the
day-to-day reference):

- **Never hardcode a hex value in component SCSS.** Use a system token:
  `--mat-sys-on-surface`, `--mat-sys-on-surface-variant` (secondary text),
  `--mat-sys-outline-variant` (borders), `--mat-sys-primary` (interactive),
  `--mat-sys-error`, `--mat-sys-secondary-container` / `--mat-sys-on-secondary-container`.
- If no token fits the semantics, write `light-dark(<light>, <dark>)` — never a
  bare hex, which would be wrong in one theme. Two sanctioned cases: the five
  `status-badge` variants (no M3 token means "warning"/"success") and the
  selected-option row (`background: light-dark(#dff3e4, #12301e)`,
  `color: light-dark(#0b5228, #9fd8b4)` — 7.9:1 light, 8.8:1 dark).
- **Do not** add `:root`/`[data-theme]` custom properties for colors — they cannot
  restyle Material components, which read `--mat-sys-*`, so a second system would
  silently diverge.

## Layout & Presentation

Responsive work is pure CSS at `max-width: 600px`, with `min-width: 601px` as its
desktop mirror. Those two values are the only breakpoints — do not introduce a
third. `BreakpointObserver` is not used: nothing here needs TypeScript to know
the breakpoint.

- **Toolbar**, left to right: app title (links to `/`) — spacer — username
  (1.1rem, `var(--mat-sys-tertiary)`) — theme toggle — Users icon button
  (`group`, admin only) — sign-out icon button (`logout`). Icon-only buttons keep
  both `aria-label` and `matTooltip`: with no visible label those are required,
  not optional. The theme toggle sits **outside** the signed-in block and stays
  visible when signed out, which is why the template has two separate
  `@if (auth.currentUser())` blocks. Below 600px the toolbar wraps: the title takes
  a full-width row (`flex: 0 0 100%`) and the trailing cluster falls beneath it,
  right-aligned by the existing `.spacer`. `height: auto` is required there —
  Material pins `mat-toolbar` to a single-row height and the wrapped row would clip.
- **Back bar**: a single `.app-back` link rendered once under the toolbar,
  visible on every route except `/challenges`, the pre-redirect root, and
  `/sign-*`. It is a plain `routerLink="/challenges"`, deliberately not a history
  `back()`: predictable, never walks the user out of the app on a deep link, no
  history bookkeeping. Accepted trade-off — from `/challenges/:id/edit` it returns
  to the list, not the detail page. Visibility is a computed over
  `NavigationEnd`'s `urlAfterRedirects`, seeded with `initialValue: router.url`
  and treating `''`/`'/'` as the list so the bar cannot flash on load; the URL is
  split on `?` so a future query string can't defeat the equality check.
- **Challenge list**: no `max-width` — the grid is
  `repeat(auto-fill, minmax(260px, 1fr))`, so a wider viewport simply fits more
  cards. The header is `justify-content: space-between` (filter left, "New
  Challenge" right); the bare `mat-select` is capped at `width: 50%` on desktop
  only. Header and grid share `--mat-sys-secondary-container` /
  `--mat-sys-on-secondary-container`, so they read as one tinted panel behind the
  neutral `mat-card`s. Card titles are `1.1rem` with `padding-left: 16px` to
  align with Material's own `mat-card-content` padding. Below 600px: single
  column, header wraps, filter returns to its intrinsic width.
- **Buttons**: labels are `white-space: nowrap` app-wide, relaxed to `normal`
  under 600px where a fixed-width button genuinely cannot fit its label.
- **Forms, detail panels, stepper actions** reflow to single column below 600px.
- **User management**: each row's delete control is a `delete` icon button whose
  `aria-label` names the specific user (`Delete jordan.patel`), so a screen-reader
  user moving down the list can tell rows apart, behind a native
  `confirm()` — stripping the word "Delete" removed the last guard against a
  mis-click.

Destructive actions use a native `confirm()`, not `MatDialog`, in both
user-management and challenge delete. A dialog component would look better and be
more accessible, but it means a new shared component plus its own spec for one
dialog's worth of polish — explicitly not taken, and one idiom beats two.

## Error Handling

`errorHandlingInterceptor` is the single routing point:

| Status | Behavior |
|---|---|
| 400 | Passed through uncaught, so the calling form can render field-level errors inline |
| 401 on a non-`/auth/` URL | `auth.clearCurrentUser()` then redirect to `/sign-in`. The API revalidates every request, so a stale `currentUser` would let a deleted or demoted user's toolbar and guards keep trusting discarded state |
| 401 on `/auth/` | Left to the caller — `/auth/me` 401s when there is simply no session, `/auth/signin` when credentials are wrong |
| 403 | Snackbar, **no redirect** — that is 401's job; bouncing on a 403 would throw an admin off `/admin/users` over one transient failure |
| 409, URL not containing `/users/` | Snackbar: the action isn't allowed in the challenge's current status. Also covers a rejected option-switch |
| 409 on `/users/` | Skipped, so user-management can say "that user still owns challenges" itself |
| ≥ 500, URL not containing `/draft-` | Generic retry snackbar |
| ≥ 500 on `/draft-` | Skipped — the draft panels render the server's message inline |

Component-level handling, deliberately narrow:

- Both draft panels hold a `draftError` signal, cleared on each attempt and set
  from `error.error?.error` when it is a string, falling back to "AI drafting is
  unavailable. Please try again." The fallback covers a network or proxy failure
  with no body, and a non-string body (`error.error` is typed `any`). It is
  rendered next to the generate button with `role="alert"` — since the generic
  ≥ 500 snackbar is excluded for `/draft-` calls, that paragraph is the only
  thing announcing the failure to a screen-reader user.
- **404 on delete** → navigate to `/challenges` anyway. Someone else deleted it
  first; the user's goal is met, and reporting a failure for an action that
  achieved its aim would be wrong.
- `user-management` surfaces what the interceptor leaves alone, and stays silent
  on 401 and ≥ 500 to avoid doubling up.
- Loading and empty states on the list and detail views.
- Do **not** add inline error handling to `selectOption` — the interceptor's 409
  snackbar already covers it.

## Testing

`npx ng test --watch=false` (Vitest) — currently **114 passing across 19 files**.
`npm run e2e` (Playwright) needs the sibling API on its `http` profile alongside
`ng serve`, and writes to the API's dev SQLite database.

Unit coverage that must hold:

- `auth.service` — `/auth/me` populating `currentUser`, 401 mapping to `null`
  without throwing, sign-in/up/out.
- `auth.guard` / `admin.guard` — redirect behavior for unauthenticated and
  non-admin access.
- `credentials.interceptor` — every request carries `withCredentials`.
- `error-handling.interceptor` — 403 snackbars without navigating; a 503 on a
  `/draft-` URL opens nothing; a 500 on a non-draft URL still opens the generic
  snackbar (that last one matters: without it the `/draft-` exclusion could
  disable the whole ≥ 500 branch unnoticed).
- `challenge-api.service` — `userId` sent, `status` omitted when null, both sent
  together, `userId` omitted with no session, and `DELETE` hitting
  `/api/challenges/{id}`.
- `challenge-list` — spinner-until-first-response, scoping to the current user,
  re-fetch on filter change, `userId` omitted for an admin, spaced status labels
  in the filter, and a byline only on challenges that aren't the viewer's.
- `challenge-detail` — the 7-case `currentPanel` exhaustiveness table,
  `loadFailed` on 404, read-only problem statement shown once accepted and not
  before, stepper ordering (asserted relatively, so inserted siblings don't break
  it), the `InReview`-only selected-option section, `canEdit` for owner /
  non-owner / admin across the edit link and delete button, a declined `confirm()`
  issuing no request, and both success and 404 deletes navigating to the list.
- `solution-options-panel` — controls hidden when `canEdit` is false and shown
  when true; at `OptionSelected` the drafting block is gone while `Select` is
  still offered on a non-selected row; the selected row carries the labelled icon
  and no `Selected` text. Assert by `aria-label`/text rather than button count
  where a count would move for more than one reason.
- `user-management` — listing, role change, delete-and-reload, the 409 owns-
  challenges message, 403 snackbars, silence on 500, and a declined `confirm()`
  issuing no DELETE. `window.confirm` is stubbed `true` suite-wide, overridden in
  the tests that decline.
- `app.component` — the title navigating home, username shown / admin link hidden
  for a collaborator, icon-only Users and sign-out buttons carrying accessible
  names, the theme toggle flipping and persisting, and the back bar absent on
  `/challenges` and present on `/admin/users` (asserted on the rendered element,
  so the template condition is covered too).
- `theme.service` — default light, restore persisted dark, toggle flipping signal
  + DOM + storage, garbage stored value falling back to light, and never emitting
  `light dark`.
- `challenge-form` — required-field validation and payload shape.
- `status-badge` — rendered label text (unaffected by `STATUS_LABELS` moving,
  which is the point of the move).

E2E: `e2e/challenge-flow.spec.ts` — sign in, create, draft/edit/accept a problem
statement, verify the list status, then delete from the detail page (the dialog
handler must be registered before the click; a pending dialog blocks every later
browser action). `e2e/auth-flow.spec.ts` — sign up → empty scoped list → create →
sign out → sign back in → the challenge persists; and a collaborator getting no
admin link and being redirected away from `/admin/users`.

Purely visual changes get no unit tests — asserting computed styles in jsdom
tests the framework, not the change. They are checked in a real browser at a
desktop width and below 600px, in both themes. A SCSS syntax error is still real,
so style-only work runs `npm run build`.

Test-mechanics facts, verified against this repo — do not re-derive:

- `httpResource` reports `isLoading() === true` with the `defaultValue` from
  creation, before any tick, so the template's `@if (loading())` guard needs no
  extra flash handling.
- `TestBed.tick()` is what issues the request; call it before `expectOne`.
- **Never `await fixture.whenStable()` before flushing a resource request** — it
  deadlocks on the pending HTTP task only `flush()` can resolve.
- After `flush()`, the value lands only after `await Promise.resolve();
  TestBed.tick();`.
- `Location.path()` strips the base href, so the root route reads `''`, not `'/'`.
- `mat-select` renders options into a `document.body` overlay that outlives the
  fixture — remove `.cdk-overlay-container` in `afterEach` or it leaks.

## Assumptions

- Lightweight auth: username + password, no email, a server-issued HttpOnly
  cookie session — not production-grade identity.
- `#070c14`/`#ffffff` is the dark-theme pair; the light theme is the derived inverse.
- Hiding owner-only controls beats disabling them with a tooltip: disabled buttons
  are an accessibility trap on touch, and a read-only page reads more clearly than
  five dead controls.
- "Unique to the user that created it" means list scoping, not a title-uniqueness
  constraint.
- A single browser tab per session; no optimistic-concurrency conflict UI.

## Deferred / Accepted Gaps

Open, and deliberately not fixed:

1. **`challenge-form`'s server-error block has no live region.** It renders
   `.challenge-form__server-errors` with no `role="alert"` and no `aria-live`, so
   a screen-reader user gets no announcement when a create or update fails — the
   same defect the two draft panels fixed. One attribute would close it; worth
   checking `sign-in`/`sign-up` at the same time, which use
   `var(--mat-sys-error)` for color but were never examined for announcement.
   Still open as of 2026-08-13.
2. **The draft panels' fallback fires for any failure status, not only
   AI-unavailable.** A 403 would produce both the interceptor's permission
   snackbar and "AI drafting is unavailable" (one of them false); a 404 would
   claim AI unavailability. Both are hard to reach because `canEdit` gates the
   buttons, and the same breadth is a small win on the 400 path, where the API's
   "Challenge has no accepted problem statement yet." now surfaces inline.
   Narrowing it means branching on status inside the panel, duplicating routing
   the interceptor owns. Revisit only if one of these combinations proves reachable.
3. **`role="alert"` is created with the element** rather than pre-existing.
   Current NVDA, JAWS, and VoiceOver all announce an inserted node that already
   carries the role, so this works; the more robust pattern is an always-rendered
   container. Change it only if a real screen-reader pass shows a missed announcement.
4. **The two draft panels' error handling stays duplicated** — about twelve
   near-identical lines whose differing parts (API method, target signal, BEM
   class) are most of them. Extraction would need inheritance for two leaves, or
   a helper that saves one `??` while adding a file, an import, and a spec.
   Trigger for revisiting: **a third draft panel.**
5. **The interceptor's `/draft-` check stays a substring check.** Only two
   endpoints contain it, path parameters are numeric ids, and no user-supplied
   text ever enters a URL (no search, no pagination). Residual risk, accepted: a
   future endpoint whose path contains `/draft-` would silently inherit the
   exclusion and lose its generic ≥ 500 snackbar. The comment at the exclusion
   states the intent.
6. **The AI-draft failure path has never been driven against a real provider.**
   Task 4 of that plan — an invalid key, confirming the inline message with no
   snackbar, then a valid key confirming Accept & Save — needs a running API and a
   real Anthropic key, so it cannot be automated. The wire contract was inspected
   on both sides and agrees (503, `{ error: <string> }`), so this is confirmation
   rather than discovery; its unique value is catching a proxy or dev-server layer
   stripping the response body, which would leave the panel showing its generic
   fallback instead of the server's message.
7. **No e2e test for the ownership rule.** Proving it end to end needs two
   concurrent browser contexts so user B can open user A's challenge — real
   harness work for a rule already covered at the component layer here and by API
   integration tests.
8. **404-before-403 leaks existence** — a non-owner learns a challenge id exists.
   Accepted at trusted-team scale; collapsing both to 404 would stop legitimate
   users telling a dead link from a forbidden one.
9. **One preservation test guards an unreachable state.**
   `problem-statement-panel`'s "shows the server message when drafting fails"
   seeds `draftText` then asserts it survives a failure. The state is not
   reachable through the UI (the draft button renders only when
   `!problemStatement && !draftText()`), but the test is cheap insurance on the
   error branch and stays. Its comment overstates its scope; the equivalent test
   in `solution-options-panel` **is** reachable and needs no caveat.
10. **Widening the challenge list to full width** is the change most likely to
    draw a follow-up opinion on a large monitor. It was the requested outcome.
11. **`height: auto` on `mat-toolbar` overrides a Material internal.** Scoped to
    the mobile media query, so a future Material version can only regress the
    narrow layout, not the desktop one.
